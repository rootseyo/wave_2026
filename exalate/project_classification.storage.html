이번 전환의 핵심

Cloud로 옮기지 않는 프로젝트는 기존 HMG Jira ↔ ADE 연결을 유지하고, 옮기는 프로젝트는 HMG Jira Cloud ↔ ADE 신규 연결로 전환합니다. ADE에서는 기존 프로젝트와 기존 이슈를 계속 사용하며, 동기화 연결 관계와 전환 중 변경분이 이어지도록 준비합니다.

1. 목적과 비교 기준

HMG와 ADE는 조직명입니다. 본 문서는 HMG Jira의 일부 프로젝트를 Cloud로 이관할 때 운영유지보수 파트와 마이그레이션 담당자가 변경해야 할 Exalate 연결 및 Trigger 범위를 정리합니다.

이관 범위: 저장소 루트의 projects.txt (고유 프로젝트 키 614개)

5. Trigger를 어떻게 나눌 것인가

각 Trigger의 프로젝트 조건만 이관 여부에 맞게 분리하고, 이슈 유형·연동 여부·생성일 등 기존 업무 조건은 유지합니다. Cloud에서 필드 ID가 달라지는 조건은 대응 필드로 변환하여 검증합니다.

  • REQ_IVI: 기존 HMG에는 CCRCTRACK·POIPTRACK만 남기고, 나머지 17개 프로젝트는 Cloud Trigger로 구성합니다.
  • CPMS: 문제점 Trigger는 기존 HMG 9개 / Cloud 24개로 분리합니다. 설계변경 Trigger의 ISCMMOBIS·ISCMAUMOVI·ISCMVEONEE는 Cloud로 전환합니다. ADEPRK 전용 Trigger는 기존 HMG에 유지합니다.
  • CPMS_IVI / FREQ / NE1a / REQ_ELEC: 현재 JQL의 프로젝트는 모두 이관 대상입니다. Cloud용 Trigger를 준비하고 기존 경로 종료는 이슈 연결 전환과 함께 처리합니다.

예시 — 기존 HMG에 남길 REQ_IVI Trigger

true

CPMS_IVI의 생성일 조건 및 cf[38210] != O, REQ_ELEC의 이슈 유형·스프린트 등록 조건도 함께 검토합니다. ADE 측에서 기존 HMG와 Cloud로 보내는 대상이 겹치지 않도록 양쪽 Sync Rule과 Trigger를 대조해야 합니다.

Trigger 변경과 기존 이슈 연결 전환은 별도 작업

Trigger JQL 수정만으로 이미 동기화 중인 이슈의 연결 관계가 Cloud로 이전되지는 않습니다. 기존 HMG 이슈 ↔ ADE 이슈 ↔ 이관된 Cloud 이슈의 대응 목록을 확보하고, 지원되는 연결 승계 또는 재연결 절차를 사전 검증해야 합니다. 신규 Connection에서 기존 이슈를 일괄 신규 동기화하여 ADE에 중복 생성하지 않도록 합니다.

6. 전환 순서와 완료 기준

  1. 범위 확정: 운영유지보수 파트는 위 12개 프로젝트의 기존 연동 유지 여부와 ADEPRK 식별을 확인하고, 마이그레이션 담당자는 최종 projects.txt를 확정합니다.
  2. Cloud 연결 준비: HMG Jira Cloud ↔ ADE 신규 Connection을 구성합니다. ADE의 기존 프로젝트 매핑, 양방향 Sync Rule, 사용자·상태·커스텀필드 매핑을 검증합니다.
  3. 기존 이슈 연결 준비: 현재 동기화 중인 이슈 쌍과 이관 후 Cloud 이슈의 대응 목록을 확보합니다. 제품 버전과 부분 이관 범위에 맞는 연결 승계 방법을 Exalate 지원 측과 확정하고 테스트 환경에서 검증합니다.
  4. 전환 시점 통제: 이관 대상의 기존 경로 동기화를 일시 정지하고 대기 건·변경분을 확인합니다. 혼재 Connection인 REQ_IVI·CPMS를 전체 정지하면 이관 제외 프로젝트도 영향을 받으므로 중단 범위와 시간을 사전 합의합니다.
  5. 경로 전환: 기존 HMG Trigger에는 이관 제외 프로젝트를 남기고, Cloud 신규 연결에서 기존 ADE 이슈와의 연결을 이어갑니다. 검증 전 구·신 경로가 같은 이슈를 동시에 처리하지 않도록 합니다.
  6. 동기화 재개 및 인수: 이관 대상은 Cloud ↔ ADE, 이관 제외 대상은 기존 HMG ↔ ADE에서 양방향 변경을 확인합니다. 중복 이슈·누락 변경·오류 및 잔여 대기 건이 없는지 확인 후 완료합니다.
